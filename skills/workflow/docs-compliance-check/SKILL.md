# docs-compliance-check

验证代码修改后 `docs/` 目录规范的同步更新，确保文档与代码一致。

## 触发条件

满足以下任一条件时自动加载：

- 用户说："检查 docs 规范"、"验证文档"、"docs 合规"
- 用户说："按 bootstrap.md 执行"、"对照 docs"
- 修改了架构、配置、新增功能等可能影响 docs 的代码后
- 用户说："完成 todo 后检查 docs"

## 核心原则

**docs 与代码同步原则**：

```
代码变更
    ↓
评估影响范围
    ↓
├─ 架构变更 → 更新 arch.md
├─ 功能变更 → 更新 prd.md
├─ 测试变更 → 更新 test.md
├─ 状态变更 → 更新 project_state.md
├─ 启动规范 → 更新 bootstrap.md
└─ 仅文档 → 更新对应文档
```

**违反案例**（来自历史对话）：

| 对话 | 问题 | 后果 |
|------|------|------|
| `0004e71a` (7/30) | 修改拖拽/展开按钮但未更新 docs | 后续按 docs 排查时遗漏 |
| `74999dc6` (7/29) | plan 执行后未清理 update 文件 | 文档堆积 |
| `a084a749` (7/29) | todo 完成后未验证 docs 规范 | 文档与实际不一致 |

## 标准检查流程

```
1. 识别代码变更范围
   ↓
2. 确定涉及的 docs 文件
   ├─ 架构变更 → arch.md
   ├─ 功能新增/修改 → prd.md
   ├─ bug 修复 → project_state.md（登记 ISS）
   ├─ 测试相关 → test.md
   ├─ 启动/部署 → bootstrap.md
   └─ 新增模块 → 新建对应文档
   ↓
3. 对照 docs 检查
   ├─ 内容是否仍然准确
   ├─ 是否需要新增章节
   ├─ 是否需要删除过时内容
   └─ 是否需要更新 ISS 状态
   ↓
4. 执行文档更新
   ↓
5. 验证更新
```

## 详细检查项

### 1. project-structure.md 标准文档结构

每个项目必须有 `docs/project/` 下的标准文档：

```
docs/
└── project/
    ├── bootstrap.md       # 启动规范与文档索引（入口）
    ├── prd.md            # 产品需求文档
    ├── arch.md           # 技术架构文档
    ├── project_state.md  # 项目状态与已知问题
    ├── test.md           # 测试规范
    └── git-usage.md      # Git 使用规范
```

**检查清单**：

- [ ] bootstrap.md 存在且为最新版本
- [ ] prd.md 反映了当前功能范围
- [ ] arch.md 与代码架构一致
- [ ] project_state.md 记录了所有 ISS
- [ ] test.md 通过率表格是最新的
- [ ] git-usage.md 反映了实际的提交格式

### 2. bootstrap.md 启动规范

bootstrap.md 应包含：

```markdown
# 项目启动规范

## 文档索引
[其他文档的快速链接]

## 项目概览
[项目目标、技术栈、目录结构]

## 启动方式
[本地开发、生产部署的命令]

## 核心规范
[编码规范、命名约定、禁止行为]

## 修改边界
[哪些可以修改、哪些需要评审]

## 文档更新流程
[修改文档的流程和审批]
```

**检查项**：

- [ ] 文档索引完整且链接有效
- [ ] 启动命令可执行
- [ ] 核心规范无遗漏
- [ ] 修改边界清晰

### 3. prd.md 产品需求

**检查项**：

- [ ] 核心/非核心功能边界明确
- [ ] 用户流程完整
- [ ] 页面/功能清单与实现一致
- [ ] 验收标准可测试
- [ ] 新增功能有对应条目

### 4. arch.md 技术架构

**检查项**：

- [ ] 模块划分表格与代码一致
- [ ] 数据流图反映最新架构
- [ ] 技术栈表格是当前使用的
- [ ] 部署链路命令可执行
- [ ] 目录结构文件树是当前的
- [ ] 可观测性章节描述实际监控
- [ ] 已知架构债引用 ISS 编号

### 5. project_state.md 项目状态

**检查项**：

- [ ] 当前阶段准确（开发中/测试/生产）
- [ ] ISS 编号连续
- [ ] ISS 状态最新（🟨/🟩/❌）
- [ ] 下一步行动明确
- [ ] 项目统计数据准确

**ISS 表格格式**：

```markdown
| 编号 | 问题 | 优先级 | 状态 |
|------|------|--------|------|
| ISS-001 | 问题描述 | P1/P2/P3 | 🟨 待处理 |
| ISS-002 | 问题描述 | P1 | 🟩 已完成 |
```

**强制要求**：

- 新增 bug 必须登记 ISS
- 修复完成必须更新状态为 🟩
- 不修复必须更新状态为 ❌ 并说明原因

### 6. test.md 测试规范

**检查项**：

- [ ] 测试目录结构与实际一致
- [ ] 测试层级划分明确
- [ ] **通过率表格真实记录**（禁止写死 PASS）
- [ ] 上次运行日期 ≤ 7 天
- [ ] 退出码符合约定（0=通过，1=断言失败，2=脚本异常）

**通过率表格格式**：

```markdown
| 脚本 | 上次运行日期 | 退出码 | 备注 |
|------|-------------|--------|------|
| `tests/test_solver.py` | 2026-08-30 | 0 | 8 项 |
| `tests/test_models.py` | 2026-08-30 | 0 | 13 项 |
```

### 7. git-usage.md Git 规范

**检查项**：

- [ ] 提交格式与实际一致
- [ ] 分支模型清晰
- [ ] 反模式清单完整

## 实施步骤

### Step 1：识别变更

```bash
git diff --name-only HEAD~1 HEAD
git diff --stat HEAD~1 HEAD
```

按变更类型分类：

| 变更类型 | 影响 docs |
|---------|----------|
| 新增模块 | bootstrap、arch |
| 新增功能 | prd |
| 修改架构 | arch |
| 修复 bug | project_state（登记 ISS） |
| 新增测试 | test |
| 修改配置 | bootstrap |
| 修改提交格式 | git-usage |

### Step 2：加载相关规则

```yaml
rules_to_check:
  - project-structure.md
  - 具体文档路径
```

### Step 3：对照检查

使用检查清单（见上文）。

### Step 4：生成报告

```markdown
## Docs 合规检查报告

**变更范围**：<模块/功能>
**检查时间**：YYYY-MM-DD

### 检查结果

| 文档 | 状态 | 需要更新 |
|------|------|---------|
| bootstrap.md | ✓/✗ | 是/否 |
| prd.md | ✓/✗ | 是/否 |
| arch.md | ✓/✗ | 是/否 |
| project_state.md | ✓/✗ | 是/否 |
| test.md | ✓/✗ | 是/否 |
| git-usage.md | ✓/✗ | 是/否 |

### 待更新项

1. <更新内容 1>
2. <更新内容 2>

### ISS 登记

- [ ] 新增 ISS-XXX：<问题描述>
- [ ] 更新 ISS-XXX 状态为 🟩
```

### Step 5：用户确认

在执行更新前询问用户：

```
发现以下 docs 需要更新：
1. <更新 1>
2. <更新 2>

是否执行更新？
- 是
- 否（暂不更新）
- 仅更新部分（用户指定）
```

### Step 6：执行更新

按报告逐项更新 docs。

### Step 7：验证

- 重新对照检查清单
- 确认所有变更已反映在 docs 中

## 注意事项

### 必须遵守

- **强制**对照 docs 检查所有代码变更
- **强制**登记 ISS 编号跟踪 bug
- **强制**更新测试通过率表格（不写死 PASS）
- **禁止**删除 docs 中的过时内容（标记为废弃）
- **禁止**跳过 docs 检查就直接提交

### 推荐实践

- 修改前先读相关 docs
- 修改后立即更新 docs
- 跨模块变更时同时更新多个 docs
- 提交信息中说明 docs 更新

### 反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 修改代码不更新 docs | 文档失真 | 强制检查清单 |
| 测试通过率写死 PASS | 失真 | 实际运行后记录 |
| ISS 不编号 | 难以跟踪 | 强制 ISS-NNN 编号 |
| 删除过时 docs 内容 | 失去历史 | 标记为废弃而非删除 |
| 跳过 docs 检查 | 提交后才发现问题 | 提交前必检查 |
