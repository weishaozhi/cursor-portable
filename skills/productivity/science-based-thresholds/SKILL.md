# 科学设定阈值（Science-Based Thresholds）

> 适用于：规则触发阈值、技能整理阈值、告警阈值、性能阈值、缓存阈值、批处理阈值等任何需要"设定一个数字"的场景。

## 适用场景

- 📊 **知识管理**：规则触发阈值、技能整理阈值、文档归档阈值
- 📊 **系统监控**：告警阈值、SLO 阈值、性能告警阈值
- 📊 **性能优化**：缓存大小、连接池容量、批处理批次
- 📊 **业务逻辑**：重试次数、超时时长、限流阈值
- 📊 **用户体验**：表单字段数、菜单层级、加载等待时长
- 📊 **数据处理**：采样率、聚合窗口、数据保留期

---

## 核心方法论

### 五步法（Five-Step Framework）

```
1. 收集数据 → 2. 引用理论 → 3. 对比实践 → 4. 设定缓冲 → 5. 持续验证
```

---

## 第一步：收集数据（Evidence Collection）

**关键问题**：
- 当前的规模是多少？（项目数、技能数、用户数等）
- 历史趋势是怎样的？（增长、稳定、下降）
- 哪些维度需要阈值？（数量、时间、频率等）

**数据收集清单**：
```
□ 总量统计
  ├─ 整体规模（如：技能总数）
  ├─ 分类规模（如：单分类技能数）
  └─ 增长趋势（如：每月新增量）

□ 使用模式
  ├─ 高频使用项（前 20%）
  ├─ 中频使用项（中间 60%）
  └─ 低频使用项（后 20%）

□ 历史事件
  ├─ 已出现的"过载"案例
  ├─ 已废弃的项目（自然淘汰）
  └─ 用户反馈的痛点
```

**示例**（知识沉淀场景）：
```
你的项目数据：
├─ 项目数：9 个
├─ 规则数：8 个
├─ 技能总数：41 个
│  ├─ 活跃：28 个
│  ├─ 进行中：9 个
│  └─ 废弃：4 个
└─ 分类统计：engineering 13 个、productivity 5 个...
```

## 第二步：引用理论（Theoretical Foundation）

| 理论 | 数值 | 适用场景 | 引用 |
|------|------|---------|------|

| 实践 | 阈值 | 适用场景 |

|------|---------|------|

|------|------|------|
| **加载等待** | < 1 秒（无反馈） | Nielsen Norman Group |
| **表单字段** | **5-7 个分组** | 米勒定律应用 |
| **菜单层级** | **≤ 3 层** | 信息架构经验 |

| 指标 | 阈值 | 依据 |
|------|------|------|

| **超时时长** | **30 秒**（用户操作） | UX 等待耐心 |
| **数据保留期** | **90 天 / 1 年** | 业务周期 + 合规 |

## 第三步：对比实践（Compare with Reality）

**关键问题**：
- 当前实践的数值是多少？
- 与理论建议相差多少？
- 偏差的原因是"我们不同"还是"理论不适用"？

**对比矩阵模板**：
```
指标           │ 理论建议  │ 当前实践  │ 偏差  │ 原因分析
────────────────┼──────────┼──────────┼───────┼─────────
单分类技能数    │ 9-15     │ 13       │ -2    │ 仍在区间
全局技能数      │ 50       │ 41       │ -9    │ 还有空间
规则触发次数    │ 3        │ 待收集   │ ?     │ ?
用户表单字段    │ 5-7      │ 12       │ +5    │ 业务需要
```

**判定规则**：
- ✅ 偏差 < 20%：理论可直接应用
- ⚠️ 偏差 20-50%：需调整 + 记录原因
- ❌ 偏差 > 50%：需深入分析，可能理论不适用

## 第四步：设定缓冲（Buffer Zone）

### 缓冲策略

#### 1. **提前介入（Proactive）**
```
触发阈值 = 理论上限 × 0.75

示例：
- 单分类技能理论上限 = 15
- 触发整理阈值 = 15 × 0.75 = 12... 
- 但考虑认知舒适区 = 9-15
- 综合判定：15 个时触发（保留 50% 缓冲时间）
```

#### 2. **分级阈值（Tiered）**
```
警告阈值 = 理论上限 × 0.75   → 提醒
强制阈值 = 理论上限 × 1.0    → 必须处理
紧急阈值 = 理论上限 × 1.25   → 立即处理

示例：
- 单分类技能
  ├─ 10 个：黄色警告（提醒整理）
  ├─ 15 个：橙色强制（建议整理）
  └─ 20 个：红色紧急（必须整理）
```

#### 3. **缓冲公式**
```
最终阈值 = 理论值 × 情境系数 × 安全系数

情境系数：
├─ 高频场景（每天用）= 0.7（更严格）
├─ 中频场景（每周用）= 1.0（标准）
└─ 低频场景（每月用）= 1.3（更宽松）

安全系数：
├─ 关键路径 = 0.8（提前介入）
├─ 一般流程 = 1.0（标准）
└─ 实验性功能 = 1.2（允许更多探索）
```

## 第五步：持续验证（Continuous Validation）

### 监控机制

```
□ 数据收集（每周/每季度）
  ├─ 实际触发频率
  ├─ 误判次数（不该触发但触发了）
  └─ 漏判次数（该触发没触发）

□ 效果评估
  ├─ 阈值设定后，问题减少了多少？
  ├─ 用户反馈如何？
  └─ 是否有新的痛点？

□ 阈值调整
  ├─ 数据支撑的调整（有证据）
  ├─ 用户反馈的调整（主观感受）
  └─ 理论更新的调整（新研究）
```

### 调整周期

| 阈值类型 | 调整周期 | 触发条件 |
|---------|---------|---------|
| **用户认知类** | **3 个月** | 用户反馈 ≥ 3 次 |
| **性能类** | **1 个月** | 数据偏离 ±20% |
| **业务类** | **6 个月** | 业务变化时 |
| **归档类** | **6 个月** | 季度评审 |

## 常见陷阱（Anti-Patterns）

### ❌ 陷阱 1：复制粘贴阈值
```
错误：别人用 100，我就用 100
正确：根据你的数据 + 理论推导
```

### ❌ 陷阱 2：阈值即真理
```
错误：设定了就不再改
正确：每季度验证，根据数据调整
```

### ❌ 陷阱 3：单一维度
```
错误：只看数量
正确：数量 + 时间 + 频率 + 成本
```

### ❌ 陷阱 4：没有缓冲
```
错误：阈值 = 上限
正确：阈值 = 上限 × 0.75（提前介入）
```

### ❌ 陷阱 5：忽略上下文
```
错误：所有场景用同一阈值
正确：高频更严，低频更宽
```

## 快速决策树

```
需要设定阈值？
    │
    ├─ 有理论依据？
    │   ├─ 是 → 用理论值 × 0.75-1.0
    │   └─ 否 → 有类似场景的经验值吗？
    │       ├─ 是 → 参考 + 验证
    │       └─ 否 → 从保守值开始，逐步调整
    │
    ├─ 有数据支撑？
    │   ├─ 是 → 对比理论，偏差 < 20% 直接用
    │   └─ 否 → 先收集 2 周数据再设
    │
    └─ 有验证机制？
        ├─ 是 → 设阈值 + 监控 + 调整循环
        └─ 否 → 必须先建立监控
```

## 实战案例

### 案例 1：技能整理阈值（本次实践）

**问题**：技能数量到什么程度应该整理？

**步骤 1：收集数据**
- 当前：28 个活跃技能
- 分类：engineering 13 个，productivity 5 个
- 历史：4 个已 deprecated

**步骤 2：引用理论**
- 米勒定律：单分类 7±2 = 9-15
- 邓巴数字：密切关系 = 15
- 三次法则：规则违反 3 次触发

**步骤 3：对比实践**
- engineering 13 个 vs 理论 9-15 → 在区间内
- 全局 41 个 vs 理论 50 → 仍有空间

**步骤 4：设定缓冲**
```
单分类:
  舒适 ≤ 9, 警告 9-12, 必须整理 > 12, 紧急 > 15

最终阈值: 15（保留缓冲，接近理论上限时介入）
```

**步骤 5：持续验证**
- 检查频率：每 10 次对话或每周
- 评估周期：每季度
- 调整条件：误判率 > 20% 或漏判率 > 20%

### 案例 2：API 重试阈值

**问题**：API 失败应该重试几次？

**步骤 1：收集数据**
- 当前：固定重试 3 次
- 失败模式：网络超时、5xx 错误、4xx 错误

**步骤 2：引用理论**
- 三次法则：3 次重复即抽象
- 指数退避：1s, 2s, 4s
- 业务容忍：30 秒总超时

**步骤 3：对比实践**
- 3 次重试 + 指数退避 = 1+2+4 = 7 秒（< 30 秒 ✓）

**步骤 4：设定缓冲**
```python
max_retries = 3          # 重试次数
backoff_factor = 2       # 指数因子
max_total_time = 30      # 总超时

# 计算: 1s + 2s + 4s = 7s（占 30s 的 23%，缓冲充足）
```

**步骤 5：持续验证**
- 监控：重试成功率、重试总耗时
- 调整：如果重试成功率 < 50%，考虑熔断

## 总结

> **科学设定阈值的本质**：
> 不是找"正确答案"，而是建立"可解释、可验证、可调整"的方法论。

```
有理论 → 推导初始值
有数据 → 验证合理性
有缓冲 → 提前介入
有验证 → 持续优化
```

**记住**：阈值不是"精确的数字"，而是"决策的边界"。边界清晰比边界精确更重要。
