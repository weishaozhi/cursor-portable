# extract-skills-from-history

从历史对话（agent transcripts）中识别高频问题模式，并沉淀为可复用的项目级技能。

## 触发条件

满足以下任一条件时自动加载：

- 用户说："从历史对话中沉淀技能"、"分析历史问题模式"
- 用户说："哪些问题可以沉淀"、"识别技能候选"
- 用户说："extract skills"、"沉淀技能"
- 项目持续运行超过 30 天，技能库增长缓慢
- 完成阶段性工作，需要回顾经验

## 核心原则

**沉淀决策矩阵**：

```
                高频次(≥3)
                    │
                    ↓
            ┌───────────────┐
            │  沉淀为技能    │
            └───────────────┘
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   高耗时       可复用       含3+步骤
       │            │            │
       └────────────┴────────────┘
                    ↓
              触发沉淀
```

**两个判断标准**（用户共识）：

| 沉淀为 | 标准 | 存放位置 |
|--------|------|----------|
| **规则** | 核心指令（代码风格、语言选择、禁止语法） | `.cursor/rules/` |
| **技能** | 具体方法（解决问题的工作流） | `.cursor/skills/` |

## 标准工作流

```
1. 数据收集
   ├─ 读取 agent transcripts 目录
   ├─ 提取对话元数据（时间、长度、首条消息）
   └─ 收集所有可用对话（默认全部）
       ↓
2. 关键词提取与聚类
   ├─ 提取每条对话的关键词
   ├─ 合并同义/相似的关键词
   └─ 形成问题模式（≥3 次）
       ↓
3. 频率与痛点分析
   ├─ 统计每个模式的出现次数
   ├─ 判断用户痛点强度（直接表达 or 反复处理）
   └─ 评估沉淀价值
       ↓
4. 决策讨论（grilling 模式）
   ├─ 质疑分类准确性
   ├─ 讨论阈值合理性
   ├─ 确认形式选择（技能 vs 规则）
   └─ 确定优先级
       ↓
5. 创建技能
   ├─ 创建分类目录
   ├─ 按统一模板生成 SKILL.md
   ├─ 更新 INDEX.md 和 README.md
   └─ 验证可触发性
       ↓
6. 跟踪与优化
   ├─ 观察使用频率
   └─ 根据实际效果调整
```

## 详细步骤

### Step 1：数据收集

#### 1.1 定位对话目录

```
agent transcripts 目录：
C:\Users\<user>\.cursor\projects\<project-name>\agent-transcripts\
```

文件命名：`<uuid>.jsonl`，每行一个 JSON 对象，包含对话轮次。

#### 1.2 提取元数据

使用脚本扫描所有 .jsonl 文件，提取：

```python
import json
from pathlib import Path

transcripts_dir = Path(r"C:\Users\wsz\.cursor\projects\d-ai-projects\agent-transcripts")
metadata = []

for jsonl_file in transcripts_dir.glob("*.jsonl"):
    with jsonl_file.open(encoding="utf-8") as f:
        for line in f:
            try:
                record = json.loads(line)
                # 提取关键信息
                if "type" in record and record["type"] == "user_message":
                    metadata.append({
                        "file": jsonl_file.name,
                        "message": record.get("message", "")[:200]
                    })
                    break  # 只取每条对话的第一条用户消息
            except json.JSONDecodeError:
                continue
```

#### 1.3 数据量评估

```
对话数量     →   处理策略
< 20        →   全量手工分析
20-100      →   关键词聚类 + 抽样验证
100-500     →   关键词聚类 + 频率统计
> 500       →   引入 LLM 辅助聚类
```

### Step 2：关键词提取与聚类

#### 2.1 关键词提取规则

**强信号词**（高优先级）：

| 类别 | 关键词 |
|------|--------|
| 项目名 | @项目名、ciallo、md_editor、toolbox_hub |
| 动作 | 强制关闭、清理、修复、审计、检查 |
| 问题 | 失败、冲突、超时、报错、不一致 |
| 模式 | plan、docs、配置、端口、进程 |

**弱信号词**（需结合上下文）：

| 类别 | 关键词 |
|------|--------|
| 通用 | 更新、修改、增加 |
| 模糊 | 这个、那样、问题 |

#### 2.2 聚类方法

```
对话 1: "强制关闭不彻底" + "端口仍被占用"
对话 2: "启停与强杀逻辑审查"
对话 3: "强制关闭后 3000 端口仍可访问"
对话 4: "缺少 force-stop 按钮"

     ↓ 提取共同特征

关键词集合 = {"强制关闭", "进程清理", "子进程", "端口释放"}
     ↓ 形成模式

模式 = "process-tree-cleanup"（进程树清理）
```

#### 2.3 模式命名规范

| 命名风格 | 适用 | 示例 |
|---------|------|------|
| `<domain>-<action>` | 通用 | `plan-executor`, `port-config-audit` |
| `<action>-<target>` | 单一目标 | `process-tree-cleanup`, `docs-compliance-check` |
| `<scope>-<purpose>` | 复合 | `pre-commit-verify` |

**禁用**：

- 中文名（技能 ID 必须英文）
- 缩写词（如 "ptc"，降低可发现性）
- 项目特定名（如 "ciallo-fix"，应通用化）

### Step 3：频率与痛点分析

#### 3.1 频率统计

```python
from collections import Counter

pattern_counter = Counter()
for convo in conversations:
    for pattern in extract_patterns(convo):
        pattern_counter[pattern] += 1
```

#### 3.2 痛点强度评估

| 强度 | 信号 | 沉淀建议 |
|------|------|---------|
| **HIGH** | 用户明确表达痛苦（如"再不解决不行"） | 必须沉淀 |
| **MEDIUM** | 反复处理同一类型 | 建议沉淀 |
| **LOW** | 偶发，无需每次处理 | 暂不沉淀 |

#### 3.3 沉淀价值评估矩阵

```
频率 ≥ 3 次        可复用（步骤可重复）    → 沉淀
频率 ≥ 3 次        仅一次性使用           → 暂不沉淀
频率 < 3 次        可复用                → 暂不沉淀
频率 < 3 次        仅一次性使用           → 不沉淀
```

### Step 4：决策讨论（grilling 模式）

**不要直接创建**，先用 grilling 技能与用户讨论：

#### 必问问题

1. **分类准确性**
   - "我对对话的分类，你认可吗？"
   - "哪些被误判了？哪些被遗漏了？"

2. **阈值合理性**
   - "重复 N 次即抽象，这个 N 合理吗？"
   - "不同类别是否需要不同阈值？"

3. **形式选择**
   - "沉淀为技能还是规则？"
   - "用户回答：'只写最核心的指令作为规则，具体方法作为技能'"

4. **范围与优先级**
   - "本次会话创建哪些？"
   - "按什么排序？（频率/严重度/ROI）"

5. **验证机制**
   - "创建后如何验证？"
   - "多长时间复审？"

#### 不要替用户决定

- 不要直接确定优先级
- 不要直接建议创建数量
- 不要跳过验证环节

## 实际案例

### 案例 1：toolbox_hub 项目技能沉淀（2026-08-30）

**背景**：

- 项目持续运行 30+ 天
- 累积 43+ 个对话
- 用户希望识别高频问题模式

**执行过程**：

1. **数据收集**：
   - 读取 agent-transcripts 目录
   - 提取 43 个对话的第一条用户消息
   - 整理元数据

2. **关键词聚类**：
   - 提取每条对话的关键词
   - 合并同义关键词
   - 形成 4 个候选模式

3. **频率统计**：

| 模式 | 频率 | 痛点强度 |
|------|------|----------|
| plan 执行 | 8+ | MEDIUM |
| 进程清理 | 5+ | HIGH |
| docs 合规 | 5+ | MEDIUM |
| 端口审计 | 4+ | MEDIUM |
| 提交验证 | 3+ | MEDIUM |

4. **决策讨论**（grilling 7 个问题）：
   - 分类准确性 ✓
   - 阈值合理性 ✓
   - 形式选择：技能（不是规则）✓
   - 范围：5 个 P0/P1 ✓
   - 优先级：按频率排序 ✓
   - 验证：立即验证 ✓

5. **创建技能**：
   - 5 个 SKILL.md 文件
   - 共 51.8 KB，2,112 行
   - INDEX.md 和 README.md 更新

6. **元技能沉淀**：
   - 本次"从对话中沉淀技能"过程本身值得沉淀
   - 创建 `extract-skills-from-history`

**结果**：5 个技能 + 1 个元技能 = 6 个 SKILL.md

### 案例 2：单点 P0 问题识别

**场景**：用户在一天内多次提到"强制关闭不彻底"

**对话列表**：

```
085d14443 - "强制关闭不彻底"
4e369443 - "启停与强杀逻辑审查"
ace6b132 - "强制关闭后端口仍可访问"
ed72100e - "缺少 force-stop 按钮"
```

**分析**：

- 同一问题的不同表述
- 根因：Vite/esbuild 子进程脱链
- 解决：实现 `_force_kill_tree`

**沉淀决策**：

- 频率：4 次 → 满足阈值
- 痛点：HIGH（明确痛苦）
- 可复用：是（任何带子进程的项目都需要）
- 步骤：≥3 步（识别 → 收集 → 终止 → 验证）

**结论**：必须沉淀为技能

## 注意事项

### 必须遵守

- **强制**用 grilling 技能与用户讨论沉淀决策
- **强制**遵循频率阈值（默认 ≥3 次）
- **强制**使用统一模板创建技能
- **强制**从历史对话中提取实际案例
- **强制**更新 INDEX.md
- **禁止**替用户做优先级决策
- **禁止**未经验证就创建技能
- **禁止**一次性沉淀过多技能（建议 ≤5 个/次）

### 推荐实践

- 配合 `grilling` 技能使用
- 配合 `knowledge-evolution.md` 规则
- 每个技能附上 2-3 个真实案例
- 反模式清单要具体（不仅是"不要做错"）
- 创建后立即让用户验证
- 保留 1 个月观察期

### 反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 不与用户讨论直接创建 | 沉淀错方向 | 用 grilling 讨论 |
| 沉淀频率过低的问题 | 浪费精力 | 严格 ≥3 次阈值 |
| 项目特定问题通用化 | 失去价值 | 通用化要彻底 |
| 不更新 INDEX | 索引失真 | 每次创建同步更新 |
| 不附实际案例 | 抽象无依据 | 至少 2 个真实案例 |
| 一次性沉淀 10+ 技能 | 难验证 | 建议 ≤5 个/次 |
