# RULE: Git 工作流规范

## 触发条件
- 创建分支
- 提交代码
- 合并代码

## 强制约束

### 1. 提交命名格式（必须遵守）

**格式**：
```
<type><YYYY_MM_DD_HH_MM>_<short-snake-name>

<详细说明…>
- 新增了功能 123
- 调整 xxx
```

**示例**：
```
feature2026_08_30_14_30_add_search_feature

- 新增文件搜索功能
- 修改 api/routes.py 添加 /search 端点
- 修改前端添加搜索框组件
```

### 2. 提交类型（type）

| type | 含义 | 是否发版 |
|------|------|----------|
| `feature` | 新功能 | 视情况 |
| `bugfix` | 缺陷修复 | 累计 10 次或必修 |
| `refactor` | 重构 | 不直接发版 |
| `docs` | 文档 | 不直接发版 |
| `test` | 测试 | 不直接发版 |
| `chore` | 杂项（配置、依赖等） | 不直接发版 |

### 3. 分支模型

| 分支类型 | 命名格式 | 用途 | 基线 | 合入目标 |
|---------|---------|------|------|---------|
| `main` | 固定 | 稳定主分支 | - | - |
| `pre` | 固定 | 开发分支 | `main` | `main` |
| `feature/<topic>` | 描述性名称 | 新功能 | `pre` | `pre` |
| `bugfix/<topic>` | 描述性名称 | 缺陷修复 | `pre` | `pre` |
| `refactor/<topic>` | 描述性名称 | 重构 | `pre` | `pre` |
| `docs/<topic>` | 描述性名称 | 仅文档 | `pre` | `pre` |

### 4. 分支保护规则

- **`main` 分支**：
  - 禁止 `push --force`
  - 仅负责人可合并
  - 通过 PR 合并，禁止直接 push

- **`pre` 分支**：
  - 需要代码评审
  - 负责人 + 评审者可合并

## 禁止行为（反模式）

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 在 `main` 直接提交 | 污染主分支历史 | 拉分支走 PR |
| `commit --amend` 已推送的提交 | 改写公共历史 | 用 `git revert` 或新提交 |
| 一次提交塞 5 个不相关改动 | 难回滚、难 review | 拆成多个逻辑提交 |
| `push --force` 推公共分支 | 覆盖他人工作 | 绝对禁止 |
| 提交信息只写 "update" | 无法追溯改动原因 | 按格式写清楚改动内容 |

## 推荐实践

### 提交前检查清单
- [ ] 提交信息符合命名格式
- [ ] 单次提交只包含相关改动
- [ ] 已运行测试并通过
- [ ] 已更新相关文档（如有架构变更）

### 分支生命周期
1. 从 `pre` 创建 `feature/xxx` 分支
2. 本地开发并提交（遵循提交格式）
3. 推送到远程
4. 创建 PR 到 `pre`
5. 代码评审通过后合并
6. 删除已合并的 feature 分支
