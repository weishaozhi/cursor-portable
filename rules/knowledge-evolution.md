# RULE: 知识沉淀与持续改进

## 触发条件
- 对话结束或问题解决后
- 发现可优化的项目规则
- 识别到可复用的解决方案
- 技能数量增长到需要整理时

## 强制约束

### 1. 对话结束后的知识沉淀（必须执行）

每次解决问题后，AI **必须主动询问**用户：

**询问模板**：
```
问题已解决！在这次对话中，我使用了以下方法：

[列出关键方法/技术/模式]

📝 **知识沉淀建议**：
□ 是否将这些方法总结成技能（Skill）？
  - [ ] 项目级技能（仅 <当前项目> 使用）
  - [ ] 全局技能（所有项目复用）
  
□ 是否需要更新现有文档？
  - [ ] 更新 arch.md（架构变更）
  - [ ] 更新 project_state.md（登记 ISS）
  - [ ] 更新 test.md（测试覆盖）

请选择需要的操作，或回复"跳过"继续。
```

### 2. 技能创建的判断标准

#### 应该创建技能的场景
- ✅ 解决了**可重复的问题**（如"多进程清理"、"端口冲突处理"）
- ✅ 使用了**特定的工作流程**（如"TDD 红绿重构"）
- ✅ 包含**3 个以上步骤**的操作序列
- ✅ 未来可能**在其他项目中复用**

#### 不应该创建技能的场景
- ❌ 一次性的修复（如"修复某个 typo"）
- ❌ 项目特定的业务逻辑（应记录在 `arch.md` 或 `prd.md`）
- ❌ 简单的单步操作（如"读取文件"）

#### 技能范围判断
```
问题范围                     → 技能类型
─────────────────────────────────────
仅影响当前项目              → 项目级技能
  位置: <project>/.cursor/skills/

可在同类项目中复用          → 全局技能（带前缀）
  位置: ~/.cursor/skills/<category>/

跨技术栈、跨项目类型通用    → 全局通用技能
  位置: ~/.cursor/skills/common/

【认知负载控制】
- 单分类技能 ≤ 15 个（米勒定律 7±2 扩展）
- 常用技能核心集 ≤ 7 个（工作记忆容量）
- 整理周期：每 10 次对话或每周检查
```

### 3. 规则优化建议（主动识别）

AI 在工作过程中**主动识别**以下信号：

#### 触发规则优化建议的场景
- 📌 同一规则被违反 **2-3 次**（在不同对话中）
- 📌 规则与实际操作**产生冲突**（1 次即建议）
- 📌 规则描述**不够清晰**，导致理解偏差（2 次）
- 📌 发现规则**缺失**，导致问题重复出现（2 次相同问题）
- 📌 规则过于**严格**，阻碍正常开发（2 次反馈）
- 📌 单次建议数 ≤ **3 条**（聚焦核心问题）

#### 优化建议模板
```
⚠️ **规则优化建议**

**当前规则**：<规则文件名> § <章节>
**问题**：<规则存在的问题>
**建议**：<具体优化方案>

是否应用此优化？
- [ ] 是，更新规则
- [ ] 否，保持现状
- [ ] 讨论后决定
```

### 4. 技能整理与融合（定期维护）

当检测到以下情况时，AI **必须主动建议**整理技能：

#### 触发技能整理的信号
- 📊 技能数量 > **15 个**（项目级单分类）或 > **50 个**（全局所有分类）
- 📊 存在 **2 个以上技能**功能重叠度 > 60%
- 📊 技能调用频率统计显示 **40% 技能 6 个月未使用**
- 📊 技能之间存在**依赖链** > 3 层
- 📊 单次整理建议数 ≤ **5 条**（避免认知过载）

#### 整理策略

**1. 技能融合**
```
识别重叠技能：
  - skill-a: 创建 FastAPI 项目
  - skill-b: 初始化 FastAPI + Vue 项目
  
建议融合为：
  - scaffold-fullstack: 初始化全栈项目（支持参数选择技术栈）
```

**2. 技能分层**
```
原技能：
  - deploy-to-production (500 行，包含 build/test/deploy)

分解为：
  - build-assets (构建前端资源)
  - run-tests (运行测试套件)
  - deploy-app (部署应用)
  - deploy-to-production (编排上述 3 个技能)
```

**3. 技能归档**
```
未使用 > 6 个月 且 无依赖 → 移入 archived/
保留 README 说明归档原因
```

#### 整理流程
```
1. 生成技能使用报告
   - 调用频率
   - 重叠度分析
   - 依赖关系图

2. 提出整理方案
   - 融合建议：[skill-a + skill-b] → skill-c
   - 归档建议：skill-d (6 个月未用)
   - 分解建议：skill-e (过于复杂)

3. 用户确认后执行
   - 创建新技能
   - 更新依赖关系
   - 归档旧技能
   - 更新索引文档
```

## 工作流程

### A. 对话结束流程

```
问题解决
    ↓
AI 分析本次对话
    ↓
提取关键方法/模式
    ↓
判断是否值得沉淀 (§2 标准)
    ├─ 是 → 询问用户（§1 模板）
    │       ↓
    │   用户确认
    │       ↓
    │   创建技能/更新文档
    │       ↓
    │   登记到索引文件
    │
    └─ 否 → 结束对话
```

### B. 规则优化流程

```
工作中识别规则问题 (§3 信号)
    ↓
AI 记录问题实例
    ↓
累计 3 次相同问题？
    ├─ 是 → 生成优化建议 (§3 模板)
    │       ↓
    │   用户确认
    │       ↓
    │   更新规则文件
    │       ↓
    │   在规则变更记录中登记
    │
    └─ 否 → 继续记录
```

### C. 技能整理流程

```
定期检查 (每 10 次对话 / 每周)
    ↓
生成技能报告 (§4 触发信号)
    ↓
检测到需要整理？
    ├─ 是 → 生成整理方案
    │       ↓
    │   用户确认
    │       ↓
    │   执行融合/归档/分解
    │       ↓
    │   更新技能索引
    │
    └─ 否 → 继续监控
```

## 推荐实践

### 对话结束检查清单
- [ ] 问题是否完全解决？
- [ ] 使用的方法是否可复用？
- [ ] 是否需要更新文档？
- [ ] 是否需要创建技能？

### 规则优化检查清单
- [ ] 规则是否清晰易懂？
- [ ] 规则是否有实际案例支撑？
- [ ] 规则是否过于严格或宽松？
- [ ] 规则之间是否有冲突？

### 技能质量标准
- [ ] 技能名称清晰描述用途
- [ ] 包含触发条件和使用场景
- [ ] 有完整的步骤说明
- [ ] 包含示例和反模式
- [ ] 维护元数据（版本、使用次数）

## 禁止行为

- ❌ 对话结束后不询问知识沉淀
- ❌ 发现规则问题但不提出优化建议
- ❌ 创建过于具体、无法复用的技能
- ❌ 技能数量失控后不主动整理
- ❌ 删除技能时不记录归档原因
- ❌ 规则变更不记录在变更日志中

## 📚 阈值设定依据总结

### 规则优化触发：**2-3 次违反**
**依据**：
- 艾宾浩斯遗忘曲线：1 次可能是偶然，2-3 次表示系统性问题
- 敏捷开发 "三次法则"：重复 3 次即抽象
- 平衡：过低（1 次）易误判，过高（5 次）响应太慢

### 技能整理触发：**单分类 15 个 / 全局 50 个**
**依据**：
- 米勒定律：7±2 → 单分类上限 **9 个舒适，15 个极限**
- 邓巴数字：密切关系 15 人 → 熟悉技能 15 个
- 你的数据：当前 28 个活跃技能，已接近认知负载上限
- 整理缓冲：提前在 15 个时提醒，避免到 20+ 时难以管理

### 技能重叠度：**> 60% 建议融合**
**依据**：
- 60% 是"大部分重叠但有差异"的临界点
- < 60%：差异明显，不适合融合
- > 80%：完全冗余，应立即处理
- 60-80%：最佳融合区间

### 技能归档周期：**6 个月未使用**
**依据**：
- 遗忘曲线：6 个月不用 = 基本遗忘
- 季度周期：2 个季度未用 = 不再需要
- 你的数据：4 个 deprecated 技能证明自然淘汰存在
- 不删除只归档：保留可追溯性

### 单次建议数：**≤ 3-5 条**
**依据**：
- 米勒定律：一次处理 7±2 项信息
- 决策疲劳：选项 > 7 个会降低决策质量
- 实践经验：3 条建议（必做），5 条建议（可选）是认知舒适区

### 检查频率：**每 10 次对话或每周**
**依据**：
- 你的项目规模：9 个项目，活跃度中等
- 每周检查：捕获长期趋势
- 每 10 次对话：高频使用时及时干预
- 以先到者为准：平衡响应速度与打扰频率
